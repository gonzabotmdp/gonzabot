--- REGLA FUNDAMENTAL Python en el cluster ---
NUNCA sugerir correr python3/python directamente en ql-front. ql-front es nodo de login, NO de cómputo.
Cuando el usuario quiera ejecutar un script Python: SIEMPRE generar un sbatch. Sin excepciones.
El sbatch es la respuesta CORRECTA. Dar solo `python3 script.py` sin sbatch es INCORRECTO en este cluster.

Plantilla sbatch para Python (USAR SIEMPRE):
#!/bin/bash
#SBATCH --job-name=mi_job
#SBATCH --partition=cpu
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4
#SBATCH --mem=8G
#SBATCH --time=01:00:00
#SBATCH --output=/data/home/%u/nombre_%j.out
#SBATCH --error=/data/home/%u/nombre_%j.err
SPACK=/apps/local/spack/spack-2026b/spack/bin/spack  # store viejo (/usr/share/spack) vacío desde el 22/8, NUNCA usarlo

source /mnt/cpu-data/shared/ifimar-ai/envs/<paquete>.env
$PYTHON script.py

Numba (py-numba, disponible en spack-2026b, spack load py-numba): para loops de Python puro con millones de iteraciones secuenciales (integradores ODE/SDE paso a paso, Monte Carlo iterativo), agregar @njit a las funciones del loop da speedups reales de 50-100x+ (validado 27/8: integrador de Heun, 500k pasos, 8.9s → 0.096s, ~93x). Es la primera opción a sugerir ante un loop `for i in range(N)` con N grande y trabajo por iteración chico.
  ⚠ CRÍTICO — NO sugerir `multiprocessing`/chunking por tiempo para integración SECUENCIAL (donde el estado en el paso i depende del paso i-1, ej. cualquier integrador ODE/SDE tipo Euler/Heun/Runge-Kutta): partir el rango temporal en chunks independientes con `Pool` y cada chunk arrancando desde `initial_condition` NO reconstruye la trayectoria real — cada chunk sería una simulación distinta empezando de cero, no una continuación. Ese patrón de "paralelizar por chunks de tiempo" solo es válido si las iteraciones son independientes entre sí (ej. barrido de parámetros, no evolución temporal de un mismo estado). Para integración secuencial, Numba (@njit) es la opción correcta; multiprocessing NO sirve para acelerar el loop en sí.
